**MAJ-3 — `src/app/error.tsx` renders `<html>`/`<body>` tags, which the bundled Next 16 docs reserve for `global-error.js`; the error UI also uses the legacy `reset` instead of the documented primary `retry`.**
- Evidence: `src/app/error.tsx:7-9` — `export default function GlobalError({ error, reset })` returning `<html><body>…`. This file is `app/error.tsx`, not `global-error.tsx`; per the version-specific doc law in this repo (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md:96,163`): `error.js` renders *inside* the root layout (which already provides `<html>`/`<body>` — see `src/app/layout.tsx:67`), and "Global error UI must define its own `<html>` and `<body>` tags" — only `global-error.js`. Same doc (line 155–157): `retry()` is the primary recovery API in this version; `reset()` is the "less common" fallback. Project law (`AGENTS.md`) mandates following these docs.
- Impact: on any client runtime error, the rendered fallback produces `<html>` nested inside `<body>` (invalid DOM, React `validateDOMNesting` warnings, unpredictable UA styling of nested html/body), and the "Try again" button clears state without the re-fetch semantics users expect from this version's convention. The static export ships this boundary for every visitor.
- Fix: either rename the file to `src/app/global-error.tsx` (keeping the html/body wrapper and adding global CSS import), or drop the wrapper tags from `src/app/error.tsx:9` and switch the signature to `{ error, retry }` with `onClick={retry}`.
